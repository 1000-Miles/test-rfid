## Why

A day of testing the gate against the wallboard surfaced four separate problems:
pallet tags read as "Unregistered item", the voice announced every carton
individually, the TV lagged behind the local screen, and the board appeared not
to update in realtime at all.

---

## 1. Pallet tags now resolve — `bridge/src/passage.js`

Cartons and pallets live in **two different registries**, and the bridge only
read one:

| | Cartons | Pallets |
|---|---|---|
| Table | `operations_label_tag` | `warehouse_pallet` |
| Tag column | `epc` | `rfid_tag` |

`loadCatalogRemote()` now fetches both and merges them into one catalog, tagging
each entry with `kind: 'carton' \| 'pallet'`. Pallets are filtered server-side on
`rfid_tag=not.is.null&deleted_at=is.null`. A pallet-fetch failure is non-fatal —
cartons are the volume case and must not be lost with it.

**Verified live:** catalog went 80 → 82 entries; `BA0100000000000000000002`
resolves to "Pallet 1" in real gate events.

## 2. Carton state + outbound check — `bridge/src/passage.js`, `server.js`

`warehouse_carton` state is folded into the catalog (`state`, `receivedAt`,
`carton`), and `_outboundCheck()` flags an exit as `not-received` or
`already-shipped`.

Two deliberate safety properties:

- **Not a whitelist.** An unrecognised status reads as "no objection", so adding
  a state in Nexus can't start alarming on every passage.
- **Freshness-gated.** `stateMaxAgeMs` (30 min) — past that the gate stops
  judging rather than accusing cartons received since the last refresh.

The catalog is now **refreshed periodically** rather than loaded once at boot
(`NEXUS_CATALOG_REFRESH_MS`, default 120s, `0` disables). A boot-only load meant
cartons received after startup looked un-received and every legitimate dispatch
would alarm.

## 3. Voice announces totals, not every carton — `dashboard/src/useVoice.ts`

Movements buffer and are announced as **one line per product** when both beams
go clear — the moment nothing is in the doorway and the passage is over.

```
Arrived: 20 cartons of Test Product 7 - Yellow Cap
Arrived: Pallet 1
Checked out: 3 cartons of Test Product 8 - Purple Gloves
```

- **800ms settle** — a pallet breaks and re-makes the beams between cartons;
  firing on the first clear edge would fragment one run into several readouts.
- **12s fallback flush** — without it the board goes permanently mute on a
  reader with no GPIO, or one whose beams are stuck reading broken. A wiring
  fault must not silently disable all speech.
- **Chimes still fire per movement** — immediate confirmation a tag was caught.
- Pallets are never counted in cartons.

## 4. TV render performance — `dashboard/src/useBridge.ts`

Two render storms, both hitting the TV harder than the local PC:

- **GPI churn.** The bridge reports every beam poll (~5/s), changed or not, and
  `setGpi` built a new object each time. Now returns the same reference when
  unchanged so React bails out. **Measured: 72 renders → 1 per 15s at idle.**
- **Raw tag reads.** Every read fired `setRows` + `setTotalReads`. The wallboard
  displays none of that. Now buffered and flushed every 250ms — capped at 4
  renders/sec regardless of reader speed.

**Movements (`entry`/`exit`) are deliberately NOT buffered** — they are the point
of the board and still apply instantly.

## 5. WebSocket keepalive — `bridge/src/server.js`, `dashboard/src/useBridge.ts`

There was **no keepalive on either side**. The client only reconnected on
`onclose`, which never fires on a half-open connection.

- **Bridge:** 5s heartbeat — a protocol `ping` to reap dead sockets, plus an
  application-level `{type:'ping'}`. The second is required because browsers
  answer protocol pings in the network layer and never tell page JavaScript.
- **Client:** watchdog reconnects after 15s of silence, via `close()` so there
  is only ever one reconnect path.

> ⚠️ **This did not fix the reported symptom** (see Known Issues). It closes a
> real robustness gap and is worth keeping, but it was not the cause.

## 6. Cold-start movement hold — `dashboard/src/documents.ts`

A movement arriving before the first document fetch returned had no card to
credit, was filed as an exception, and was never revisited. It's now held until
the cards exist.

- Only when the board is genuinely empty — a reload restores docs from
  localStorage, and that path keeps its instant credit.
- Released in `finally`, so a **failed** fetch still lets movements through to
  the same exception path as before. Nothing is silently dropped.
- 10s backstop + 200-item cap for a fetch that neither resolves nor rejects.

## 7. Faster board refresh — `documents.ts`, `bridge/src/board.js`, `server.js`

- Kiosk poll `DOC_POLL_MS`: **60s → 5s**
- Bridge cache `BoardFeed.maxAgeMs`: **20s → 4s**, tunable via `BOARD_CACHE_MS`

**Both had to move together.** The bridge cached for 20s precisely because the
kiosk polled every 60 — changing only the client would re-serve the same payload
four times and change nothing on screen.

**Cost:** ~12× the Nexus read rate per screen (≈3 → ≈12 requests/min). Fine for
one wallboard; `BOARD_CACHE_MS` is the knob if screens are added.

## Known issues / not fixed

**1. Repeat scans diverge from Nexus — this was the actual cause of "the board
doesn't update in realtime".**

`applyMovement` dedups on `direction:epc` for the whole day (localStorage), so a
carton scanned the same direction twice only counts once. **Nexus has no such
rule and counts every movement.** During testing the same cartons were walked
through repeatedly (`in:BC01…4C` seven times), so the board correctly suppressed
them while the Nexus baseline climbed — looking like "nothing happens, then it
fixes itself later".

The 5s poll shortens that catch-up from ~60s to ~5s but **does not** reconcile
the rule. Whether the two systems should agree is an open design decision.

**2. No replay on reconnect.** The bridge does not resend movements missed while
a client was disconnected. They arrive via the poll instead — now ≤5s.

**3. No systemd unit for the bridge.** It died once today and stayed down until
started by hand. `bridge/LINUX.md:67-91` has the unit; its paths need adjusting
for this host (`/home/warehouse-rfid/test-rfid/bridge`, user `warehouse-rfid`).
